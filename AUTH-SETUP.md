# Серверний вхід на Cloudflare Pages

Версію не опубліковано. Поточний хостинг і його налаштування не змінено. Авторизація працює лише через Pages Functions або локальний сервер Functions; відкриття HTML через file://, Live Server чи GitHub Pages не виконує серверного захисту. Не публікуйте цю версію як звичайний статичний сайт.

## Секрети

У Cloudflare відкрийте Workers & Pages → ваш окремий Pages-проєкт → Settings → Variables and Secrets. Додайте значення з типом **Secret**:

- `PORTAL_PASSWORD` — ваш спільний пароль. Виберіть довгий унікальний пароль у менеджері паролів.
- `SESSION_SECRET` — окремий випадковий секрет щонайменше 32 символи, рекомендовано 32 випадкові байти або більше. Генеруйте його менеджером паролів. Не використовуйте пароль порталу як секрет підпису.

Налаштуйте секрети окремо для Production і Preview, якщо Preview потрібен. Не вставляйте їх у код, конфігурацію Wrangler, командний рядок або Git. Відсутні секрети блокують вхід. Зміна будь-якого секрету робить попередні сесії недійсними.

## Серверний ліміт і сесії

Створіть окрему базу Cloudflare D1, наприклад `ug-portal-auth`. Це службове сховище: каталог документів залишається у JS-конфігурації. База зберігає підписані випадкові ідентифікатори IP для ліміту спроб та випадкові ідентифікатори чинних сесій зі строками дії. Паролів, URL документів і відкритих IP у ній немає.

Виконайте SQL з `migrations/0001_auth_rate_limit.sql` у консолі D1. Або використайте Wrangler:

```text
npx wrangler d1 create ug-portal-auth
npx wrangler d1 execute ug-portal-auth --remote --file=migrations/0001_auth_rate_limit.sql
```

У Pages → Settings → Bindings додайте D1 binding з точним ім'ям `AUTH_RATE_LIMIT`, вибравши створену базу. Налаштуйте також Preview, якщо його використовуєте. Без binding або таблиць вхід не працюватиме.

Ліміт: до 10 запитів входу за 10 хвилин на IP, включно з успішними спробами; наступні отримають HTTP 429. Лічильник збільшується атомарно на сервері, а не у браузері. Люди за спільною зовнішньою IP-адресою ділять цей ліміт. За наявності WAF rate limiting можна додатково обмежити POST-запити до `/api/login` на своєму домені.

## Підготовка розгортання

Запускайте команди з папки `ug-internal-portal`:

```text
node build.cjs
node check-auth.mjs
node check-auth.mjs "C:/Program Files/Google/Chrome/Application/chrome.exe"
```

`dist` містить лише HTML, JS, CSS, зображення й `_routes.json`. Серверні файли, міграції, README, тести та секрети туди не копіюються. `_routes.json` має `include: ["/*"]` і порожній `exclude`: жоден файл порталу не обходить middleware.

Для репозиторію `dimorabuga-lgtm/UG-portal` файли `index.html`, `build.cjs`, `functions/` і `server/` розміщені безпосередньо в корені GitHub. У Pages залиште Root directory порожнім (корінь `/`), Build command — `node build.cjs`, Build output directory — `dist`, Production branch — `main`. Локальна назва папки `ug-internal-portal` не є підпапкою цього репозиторію. Папка `functions` має залишатися поряд із `dist` у корені репозиторію.

Для CLI можна скопіювати `wrangler.example.toml` у `wrangler.toml`, вказати свої назву проєкту та справжній database_id. Секретів у цьому файлі бути не повинно. Після окремого дозволу на публікацію використовуйте `npx wrangler pages deploy dist --project-name YOUR_PAGES_PROJECT` з папки порталу.

**Не використовуйте drag-and-drop у Dashboard:** він не компілює папку Pages Functions. Потрібні Git-інтеграція або Wrangler. [Документація Cloudflare](https://developers.cloudflare.com/pages/functions/get-started/).

У Pages → Settings → Runtime → Fail open / closed виберіть **Fail closed**, якщо налаштування доступне на вашому плані. Інакше після вичерпання квоти Functions хостинг може віддавати статичні файли в обхід авторизації. [Пояснення Cloudflare](https://developers.cloudflare.com/pages/functions/routing/#fail-open--closed).

Не додавайте cache rules, які кешують захищені HTML/API/JS-файли попри `Cache-Control: no-store`. Після майбутнього розгортання перевірте без cookie всі домени, включно з адресою pages.dev та Preview. Налаштування реального Cloudflare-акаунта не перевірені в цій локальній роботі.

## Локальний Functions runtime

Для перевірки в Wrangler скопіюйте конфігураційний шаблон, налаштуйте D1 та створіть локальний `.dev.vars` із двома секретами. Цей файл і `.env*` виключені з Git, а build не копіює їх у `dist`. Не публікуйте каталог проєкту цілком.

```text
npx wrangler d1 execute ug-portal-auth --local --file=migrations/0001_auth_rate_limit.sql
npx wrangler pages dev dist
```

На локальному HTTP cookie не має Secure; на HTTPS — має. Сесія діє 12 годин, cookie має HttpOnly, SameSite=Lax і Path=/. Сервер перевіряє HMAC-підпис, строк та наявність сесії у D1 на кожному захищеному запиті. Вихід видаляє cookie й відкликає сесію в D1, тому копія старого токена після виходу також не працює.

Доступ без авторизації дозволений лише до `/login` (самодостатня сторінка входу) та endpoint входу/виходу; обидва endpoint приймають лише POST із того самого origin. Логотип, CSS і JS сторінки входу вбудовані в її серверну відповідь. Решта файлів вимагає сесії.

Дозволи на Google-таблиці не змінюються. Пароль порталу не замінює їхніх власних прав доступу. Обране та історія залишаються локальними налаштуваннями браузера; пароль і cookie сесії туди не записуються.

## Межі локальної перевірки

`check-auth.mjs` виконує справжні серверні обробники з Web Crypto і SQLite та браузерний сценарій через локальний HTTP-адаптер. Тестові секрети генеруються лише в оперативній пам'яті й не виводяться. Це перевірка логіки та UI; вона не підтверджує налаштування Production, binding D1, квоти чи TLS реального Cloudflare-проєкту.

Локальні перевірки виконано: серверні тести та Chrome UI пройдено; Worker успішно скомпільовано Wrangler 4.151.3. Обліковий запис Cloudflare, production-секрети й віддалена D1 у цьому сеансі не налаштовувалися.

## Аудит перед production

Фактичні результати перевірок, зміни цього етапу та дії власника зібрано у [RELEASE-CHECKLIST.md](RELEASE-CHECKLIST.md). Додатково виконано інтеграційний тест у справжньому локальному Wrangler/workerd із D1: middleware, login/logout, кешування, невідомі маршрути та захищені статичні файли пройшли перевірку. Це не перевірка віддаленого Cloudflare-проєкту.

## Екран входу при відкритті сайту

Оновлено текст: «Введіть пароль для доступу до робочих матеріалів», додано плавну появу й індикатор запиту з підтримкою reduced motion. Без налаштованих секретів браузерний запит сторінки переходить на /login; спроба входу повертає 503, а внутрішні файли залишаються закритими. Чинна сесія пропускає форму до завершення 12 годин або натискання «Вийти». Повторно перевірено браузерний сценарій, індикатор завантаження та локальні Pages Functions/workerd з D1. Налаштування реального хостингу та історія віддаленого GitHub-репозиторію не перевірялися.

## Діагностика повідомлення про недоступний вхід

Дивіться [AUTH-DIAGNOSTICS.md](AUTH-DIAGNOSTICS.md): факти production-перевірки, умови HTTP 503, безпечні коди логів і кроки перевірки Production secrets та D1. Новий endpoint повертає X-Request-ID для пошуку відповідного серверного запису. Значення секретів, cookie та токенів журналювати або надсилати не потрібно.
