# Готовність до Cloudflare Pages

Стан на 21.10.2026: код підготовлений і перевірений локально. Production deployment не виконано. Реальні секрети, D1 binding, домени та cache rules Cloudflare-акаунта не налаштовувалися й не перевірялися.

## Змінені файли цього етапу

- `server/auth.mjs` — вихід більше не приховує збій відкликання сесії в D1.
- `build.cjs` — чиста збірка лише каталогу `dist`, перевірка шляху/символічного посилання, окрема 404-сторінка.
- `check-auth.mjs` — додаткові сценарії збою D1, методів, кешування, коректного за форматом зміненого HMAC та роботи каталогу після входу.
- `check-release.cjs` — перевірка production-каталогу, застарілих файлів, маршрутизації та точного URL графіка.
- `check-cloudflare.mjs` — інтеграційний тест справжніх Pages Functions у локальному Wrangler/workerd із D1.
- `AUTH-SETUP.md`, `README.md`, `RELEASE-CHECKLIST.md` — інструкції та фактичний результат перевірки.

Дизайн, HTML порталу, клієнтські компоненти, категорії та робочі URL цього етапу не змінювалися. `dist` — згенерований результат, а не вихідний код.

## Відтворення перевірок

З папки `ug-internal-portal` у Node.js 24:

```text
node check-release.cjs
node check-auth.mjs "C:/Program Files/Google/Chrome/Application/chrome.exe"
node check-browser.cjs "C:/Program Files/Google/Chrome/Application/chrome.exe"
```

Для інтеграційного тесту workerd потрібен локально встановлений Wrangler. Використаний і перевірений варіант:

```text
npm exec --yes --cache .qa-npm-cache --package wrangler@4.151.3 -- wrangler pages functions build --outdir .qa-functions
node check-cloudflare.mjs
```

Тест workerd використовує ізольовану копію в `.qa-runtime`, одноразові випадкові тестові значення у тимчасовому `.dev.vars` та локальну D1. Файл зі значеннями видаляється при завершенні. Усі `.qa-*` виключені з Git і не потрапляють у `dist`. Production-секрети для тестів не потрібні. Після примусового переривання тесту видаліть його `.qa-runtime/.dev.vars`, якщо він залишився. Windows може вимагати дозвіл на локальні процеси workerd/esbuild і службові файли Wrangler.

## Дії власника перед публікацією

1. Вибрати окремий Pages-проєкт; для `dimorabuga-lgtm/UG-portal` Root directory порожній або `/` (файли вже в корені репозиторію), команда збірки — `node build.cjs`, вихідний каталог — `dist`. `functions` залишається поряд із `dist` у корені проєкту.
2. Додати в Settings → Variables and Secrets два значення типу **Secret** для Production: `PORTAL_PASSWORD` і незалежний випадковий `SESSION_SECRET` (щонайменше 32 символи). Застосувати їх новим deployment. Для Preview налаштувати окремі секрети й binding, якщо Preview використовуватиметься.
3. Для нового середовища виконати обидві міграції: `migrations/0001_auth_rate_limit.sql`, потім `migrations/0002_session_presence.sql`, додати D1 binding `AUTH_RATE_LIMIT`. Для наявного production перевірити схему саме прив'язаної D1; якщо відсутня лише `session_presence`, застосувати наявну адитивну міграцію `0002`, зберігши базу, binding і секрети. Без `0002` вхід може працювати, але heartbeat повертає 503 на `UPDATE session_presence`, а список — на `SELECT`. Діагностика й відновлення: [PRESENCE-SETUP.md](PRESENCE-SETUP.md); авторизація: [AUTH-SETUP.md](AUTH-SETUP.md).
4. У Settings → Runtime вибрати **Fail closed** за наявності цього параметра; не дозволяти статичну видачу при вичерпанні Functions quota. Перевірити, що cache rules не ігнорують `no-store`. [Cloudflare routing](https://developers.cloudflare.com/pages/functions/routing/#fail-open--closed).
5. Розгортати лише після окремого дозволу через Git-інтеграцію або Wrangler. Dashboard drag-and-drop не компілює папку `functions`. [Cloudflare deployment](https://developers.cloudflare.com/pages/functions/get-started/).
6. Після контрольного розгортання повторити тести без cookie на custom domain, pages.dev і Preview: `/`, `/index.html`, `/js/portal-links.js`, `/js/app.js`, `/css/styles.css`, `/assets/ug.svg`; перевірити login/logout, Secure cookie на справжньому HTTPS, D1 та заголовки кешування через CDN.
7. Перевірити відкриття графіка обліковим записом співробітника. Права Google Sheets налаштовуються окремо; локальні тести підтверджують URL кнопки, а не право читання приватної таблиці.

## Відомі межі

Немає підтвердження конфігурації хостингу, TLS, CDN-кешу, production D1 та секретів: це потребує вашого Cloudflare-акаунта і контрольного deployment. Git-історія віддаленого репозиторію на наявність колись опублікованих секретів не перевірялася; нових production-значень у код чи публічну збірку не додано.

Вхід використовує один спільний пароль без індивідуальних ролей. Люди за однією зовнішньою IP-адресою ділять ліміт входу. База D1 потрібна для кожної перевірки сесії; при її відмові доступ закривається. GitHub Pages та звичайний статичний сервер не виконують цю авторизацію і непридатні для production цієї версії.
