# Діагностика входу ug-portal.pages.dev

Зміни цього аудиту не опубліковано. Не передавайте пароль, SESSION_SECRET, Cookie або Set-Cookie у чат чи логи.

## Факти production-перевірки

GET-запити до `https://ug-portal.pages.dev` під час цього аудиту:

| Шлях | Відповідь |
| --- | --- |
| `/`, Accept: text/html | 303 → `/login` |
| `/login` | 200, HTML форми входу, `Cache-Control: no-store, private` |
| `/api/login`, GET | 405, JSON «Метод не підтримується» |
| `/js/portal-links.js`, без cookie | 503, текст «Вхід тимчасово недоступний. Спробуйте пізніше.» |

Це підтверджує існування серверного endpoint та захист внутрішнього конфігу. Форма локально надсилає `POST /api/login`, `Content-Type: application/json`, `{password: ...}`; сервер читає те саме поле з того самого формату. Змінні беруться з `context.env` під точними назвами PORTAL_PASSWORD і SESSION_SECRET.

У наявному middleware саме відповідь 503 для захищеного JS повертається лише при невдалому `configured(env)`, до перевірки сесії й до D1. За відсутньої сесії зі справними секретами відповідь була б 401. Отже, **для поточного локального коду спостережуваний результат відповідає відсутньому/порожньому PORTAL_PASSWORD або відсутньому/коротшому за 32 символи SESSION_SECRET**.

Це не визначає, яка саме змінна некоректна. Без production-логів, налаштувань deployment та Git SHA не підтверджено також повний збіг серверного коду production із цією локальною версією. Не можна оголошувати збій D1 чи криптографії точною production-причиною лише на підставі загального повідомлення форми.

## Умови появи загальної помилки форми

Форма показує «Вхід тимчасово недоступний. Спробуйте пізніше», коли endpoint повертає помилку, відмінну від 401 (неправильний пароль) та 429 (ліміт спроб), або коли HTTP 200 не містить коректного JSON `{ok:true}`. Сервер повертає 503 при некоректних секретах, відсутньому D1 binding, помилці ліміту, криптографії чи створення сесії. Ці помилки не маскуються під неправильний пароль.

## Мінімальні зміни

- `server/auth.mjs`: централізовано коди конфігураційних проблем та безпечний журнал без значень; журналювання збою пошуку сесії.
- `functions/api/login.js`: розділено конфігурацію, відсутність binding та етапи виконання; додано випадковий `X-Request-ID` для співставлення з логом.
- `functions/_middleware.js`: журналювання конфігураційної відмови без розкриття внутрішнього вмісту.
- `functions/api/logout.js`: безпечний код збою відкликання сесії.
- `server/login-page.mjs`: виправлено обробку успіху — HTTP 200 з HTML, некоректним JSON або `{ok:false}` більше не викликає перенаправлення як після успішного входу. Дизайн і тексти не змінено.
- `check-auth.mjs`: перевірки діагностики, відсутності конфіденційних значень у логах та неправильних форматів відповіді.

## Як прочитати серверний діагноз

Після погодженого нового deployment відкрийте його runtime logs у Cloudflare Pages (або використайте `wrangler pages deployment tail` для потрібного deployment). У браузері, Network → POST `/api/login` → Response headers, знайдіть `X-Request-ID` і відповідний запис `portal_auth_failure` у логах. Не копіюйте Request Payload або Cookie.

| Код / issues у серверному лозі | Що означає та що перевірити |
| --- | --- |
| `AUTH_CONFIGURATION_INVALID` + `PORTAL_PASSWORD_MISSING` | У runtime немає непорожнього текстового PORTAL_PASSWORD. Перевірити Production secret із точною назвою. |
| `AUTH_CONFIGURATION_INVALID` + `SESSION_SECRET_MISSING` | Немає текстового SESSION_SECRET. Перевірити Production secret. |
| `AUTH_CONFIGURATION_INVALID` + `SESSION_SECRET_TOO_SHORT` | SESSION_SECRET коротший за 32 символи. Зберегти новий незалежний випадковий секрет достатньої довжини. |
| `D1_BINDING_MISSING` | У runtime немає binding AUTH_RATE_LIMIT з методом prepare. Перевірити Settings → Bindings, не Variables. |
| `RATE_LIMIT_CHECK_FAILED` | Збій на етапі ліміту: D1, таблиця login_attempts або HMAC. Перевірити binding, міграцію та стан D1; код етапу сам по собі не називає точний SQL/криптографічний виняток. |
| `LOGIN_REQUEST_READ_FAILED` | Збій читання запиту, не неправильний пароль. Перевірити HTTP-формат без виведення його вмісту. |
| `PASSWORD_CHECK_FAILED` | Серверна помилка етапу криптографічного порівняння, не повідомлення про неправильний пароль. |
| `SESSION_CREATE_FAILED` | Збій на етапі створення сесії: зокрема auth_sessions у D1 або підпис. Перевірити міграцію та стан D1. |
| `SESSION_LOOKUP_FAILED` | D1 не дозволила перевірити вже підписану сесію; доступ відхилено. |
| `SESSION_REVOKE_FAILED` | Не вдалося підтвердити відкликання; вихід повертає 503, а не хибний успіх. |

Логи містять лише event, code, випадковий requestId та перелік статичних issues. Не містять сирих Error/stack, значень або довжин секретів, запиту, IP, cookie чи токена. Неправильні паролі не записуються.

## Дії в Dashboard

1. У Workers & Pages → **ug-portal** → Settings → Variables and Secrets перевірити Production `PORTAL_PASSWORD` і незалежний випадковий `SESSION_SECRET` (не коротший за 32 символи), обидва як Secret. Значення не потрібно показувати іншим. Не створюйте пароль за замовчуванням у коді.
2. Перевірити, що це **Production**, а не лише Preview. Якщо значення збережено після поточного deployment, застосувати їх новим deployment. Повторне збереження потрібне лише коли змінна відсутня/некоректна або немає впевненості, що зміна була застосована.
3. У Settings → Bindings перевірити D1 `AUTH_RATE_LIMIT`, у прив'язаній базі — таблиці `login_attempts` та `auth_sessions` з `migrations/0001_auth_rate_limit.sql`.
4. Звірити commit SHA поточного production deployment з потрібним GitHub commit. Локально віддалений GitHub та Cloudflare-акаунт недоступні, тому цей збіг не перевірено.
5. Перевірити корінь проєкту, `node build.cjs`, output `dist`, папку `functions` у корені поряд із `dist`, `_routes.json` з `include:["/*"]`, `exclude:[]` та Fail closed. Не завантажувати лише статичні файли через Dashboard drag-and-drop. Деталі в [AUTH-SETUP.md](AUTH-SETUP.md).

## Перевірка після deployment

Без cookie: `/` веде на `/login`; `/js/portal-links.js` не віддає документів. За справної конфігурації цей JS-запит має 401, а не 503. POST із неправильним паролем має повернути JSON 401, з правильним — JSON `{ok:true}` та HttpOnly-cookie. Перевірте Secure на HTTPS, reload, вихід і недоступність старого cookie. Успішний вхід у production у цьому аудиті не перевірявся: production-пароль не запитувався й не використовувався.

Для остаточного віддаленого діагнозу достатньо **HTTP status + X-Request-ID + code/issue із відповідного безпечного логу**, а також Production deployment SHA. Не потрібні значення секретів, повні запити чи токени.

## Локальні результати

Пройдено тести справжніх серверних обробників та браузера: правильний/неправильний пароль, кожна конфігураційна відмова, відсутній/пошкоджений D1, сесія, змінений і прострочений токен, відкликання, захист файлів, CSRF, атрибути cookie, no-store, ліміт спроб. Тести підтвердили, що нові логи не містять тестових секретів, cookie, токенів або приватного тексту винятків. Окремо перевірено відмову форми від HTML 200, некоректного JSON та `{ok:false}`.

Пройдено локальний Wrangler/workerd із D1: маршрути, статичні файли, вхід/вихід та відкликання. Це не перевірка production-логіну й не зміна production-конфігурації.
